# Step 2 telemetry: forward-definition fix, energy tolerance, stage-2 table diagnosis

The change corrects two validator claims that the first server runs falsified (UDP forwards vs FlowMonitor, energy equality), adds a passive `telemetry_ip_forward_udp_delivered` counter in the C++ sim, commits the 39 server runs with stage-1 trust and stage-2 route tables, and adds `analyze_stage2_tables.py` to diagnose why TLDQN still routes through malicious relays. Reported numbers match the committed JSON reports. 108 tests pass and the C++ syntax check passes. The "TLDQN weights trust weakly" conclusion is stated as a cause in the docs but the analysis does not establish it.

Watch for: (1) the causal claim about TLDQN trust weight is overstated, since the counterfactual tests one direction only (likely); (2) the "valid" label for 39 runs covers forwarding only through necessary conditions, and the exact check is unverified until the new binary runs (confirmed); (3) the "better alternative" metric ignores link quality and progress (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The FlowMonitor root cause checks out against ns-3.48: `timesForwarded` is added to `FlowStats` only in `ReportLastRx`, and the per-packet forward counter that mirrors it is sound for this workload. The validator is honest that the legacy runs are only checked against necessary conditions, but the aggregate `all_valid: true` in the reports and the "39 run valid" bullet do not carry that qualifier.

The energy root cause also checks out: `Time * double` returns `Time` at 1 ns resolution. The tolerance is a heuristic bound (the 4 updates per PHY event is not derived from the energy model) but it is about 20x the observed pilot error, which is tight enough to catch real accounting bugs.

The stage-2 diagnosis is accurate as measured (169 to 76 sources via malicious, 46 in step 1), but the explanation offered for the residual 76 is stronger than the evidence. Labels are used only for evaluation in the new script.

## FlowMonitor forwarding: mechanism and the delivered counter

`flow-monitor.cc` adds `tracked->second.timesForwarded` to `FlowStats` inside `ReportLastRx` and erases the tracked packet; `ReportDrop` and the periodic lost check do not add it. That matches the claim, and it explains why the excess is zero when nothing is lost and correlates with grayhole drops. The C++ fix counts forwards per `(src,dst,id,proto)` and folds them into `g_totFwdUdpDelivered` at the first `LocalDeliver`, erasing the key so duplicates add nothing, which mirrors FlowMonitor's erase-on-first-rx.

Gaps relative to FlowMonitor's behavior: FlowMonitor ignores a delivery that arrives after its tracking was dropped by `CheckForLostPackets` (10 s), and ignores forwards of packets it no longer tracks. The counter has neither rule. Forwards of lost packets stay in the map for the whole run. With IDs below 65536 per flow and loss counts in the hundreds this is harmless, and it only matters if the exact check fails on the next batch.

The validator's legacy path checks `excess >= 0` and `excess == 0` when no loss. Those are necessary conditions, not equality, and the docs say so in 3.5 and in the verification table. The reports' `all_valid` and the 2d.3 bullet "39 run valid" read stronger than that.

## Energy tolerance

`BasicEnergySource::CalculateRemainingEnergy` computes `(totalCurrentA * V * duration).GetSeconds()` with `duration` a `Time`. The floating-point `operator*(Time, T)` converts through `int64x64_t` and returns a `Time`, so each update is quantized to 1 ns of joules. The documented claim holds. The bound `1e-9*(n*simTime + 4*phy_events) + 1e-6` is about 20x the pilot's 4.6 uJ against 18 J, which is a relative tolerance near 6e-6. That is meaningful for catching a missing window or a double-counted state, but would not detect sub-uJ drift. The factor 4 is not derived from the radio model.

## Stage-2 table analysis and the TLDQN trust claim

Labels enter `analyze_stage2_tables.py` only through `X.load_ground_truth` for counting malicious relays and for the counterfactual environment's `mal` argument. The routes in the committed stage-2 tables come from telemetry trust, so evaluation-only use holds, provided `build_env(..., "telemetry", tr10)` does not feed `mal` into the policy's inputs. That call was not traced here (possible).

The totals reproduce from `telemetry_step2_tables.json`: 169, 76, 46, 53 observed with 23 unobserved, 38 entries with 37 having an alternative, counterfactual 92. The alternative check treats candidates with `k >= n` as the sink (trust 1) and unobserved nodes as 0.5, which is a reasonable availability test, but it says nothing about why TLDQN rejected them.

The counterfactual maps telemetry trust into the 10-observation scale. This shrinks the dynamic range, so a worse outcome is what a weak trust weight predicts and does not separate that from an out-of-distribution input. A conclusive test is a sensitivity probe on the Q-network (change only the trust component of one candidate and watch the argmax), which needs no TLDQN change. Until then the docs should present weak weighting as the leading hypothesis.
