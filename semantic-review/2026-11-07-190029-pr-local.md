# Passive NS-3 telemetry, watchdog and offline two-stage trust (step 2)

Adds a `telem` namespace to `honeycomb-sdwsn.cc` that attaches IP/MAC/PHY/energy trace sinks to every sensor and writes per-node/window, per-link and watchdog-audit CSVs plus a meta JSON. A post-run classifier turns "AckedMpdu to j, then did the observer hear j forward it" into four watchdog categories. Python adds a schema/validator, a Beta trust built only from `obs_*`, an evaluation script (the only label join) and a `--trust-source none|telemetry` switch in `export_routes.py`. TLDQN, Bi-GAN, DTO, IPS, radio range and traffic model are untouched (checked against the diff: the only non-telem C++ edit is capturing `radioEnergyHelper.Install(...)`). The 104 Python tests pass; nothing was run in NS-3, so every runtime claim is unverified.

Watch for: (1) the energy validator will fail on real output because `metrics_*.csv` is written at 6 significant digits but compared at 1e-7 relative (confirmed); (2) strict FlowMonitor forward equality can break on TCP retransmissions (possible); (3) the `unobserved_rxfail` bucket only ever removes negative evidence, so malicious trust is biased upward in proportion to ambient RX failures (likely).

**Verdict**: NEEDS_CHANGES

## High-level view

The telemetry code is genuinely passive as far as I can trace it: trace sinks only read packets (copies), there is no scheduling, RNG or promiscuous mode, and the one post-run energy read goes through the same `UpdateEnergySource` the existing metrics code calls anyway. No label or grayhole state is reachable from `telem`, and trust consumes only the five `obs_*` columns.

The watchdog is built from timestamps after the run, which keeps it passive, but it makes the ambiguous bucket depend on any PHY failure at the observer within one second. That is a coarse heuristic that discards only drops, never forwards, so it systematically flatters malicious relays under load. The audit file measures this, which is the right mitigation, but the trust formula does not compensate.

Validation plumbing mostly matches what C++ writes (headers, window keys, truncation bookkeeping, per-window aggregation all line up). The exceptions are the energy comparison precision and the exact-equality FlowMonitor check, whose definition match holds for UDP but is fragile for TCP.

Docs are accurate except for a few overstatements listed below. Telemetry defaults to on, so every future run (including step-1 style sweeps) now writes extra files and extra metric rows.

1. **Energy validator false failure (confirmed)** — `sensor_energy_consumed_J` is written with default 6-digit stream precision (`honeycomb-sdwsn.cc:2149,2215`) but `telemetry_schema.py:226` allows only 1e-7 relative error. 2. **FlowMonitor forward equality fragile for TCP (possible)** — telemetry counts every non-fragment UDP/TCP `UnicastForward` (`:1179`, `OnUnicastForward`); FlowMonitor only counts if the packet is still tracked. A TCP retransmit of an already delivered or dropped segment carries the old tag and is forwarded but not counted by FlowMonitor. Compare UDP-only forwards, or report the TCP delta separately, and check the pilot log for the warning before treating it as a bug.
3. **Upward trust bias from rxfail discard (likely)** — a dropped packet is moved to `unobserved_rxfail` (dropped from trust) whenever the observer logged any RX failure in 1 s (`:1498-1501`); forwarded packets never are. Report trust sensitivity with and without discard, or shrink the failure window / restrict to failures overlapping j's likely transmit time; at minimum state the bias in `docs/TELEMETRY.md`.
4. **`unobserved_clean` counted as negative evidence without a miss-rate guard (likely)** — "clean" also covers j transmissions the observer missed silently (preamble never detected, observer transmitting, below sensitivity) and benign j queue/ARP drops. Gate trust use on the audit `unobserved_clean_observer_miss_frac` from the pilot.
5. **`self_*` forwarding counters sit in the telemetry CSV (confirmed, by design)** — `self_ip_fwd_*` and `self_ip_drop_route_error` expose grayhole behaviour directly. Trust ignores them, but any later consumer (step 3 evidence) can leak; keep them in the separate file or enforce the exclusion in a shared loader.
6. **Sensor forward sum vs network total (confirmed, minor)** — `self_ip_fwd_pkts` counts all protocols and fragments while `telemetry_ip_forward_total` counts UDP/TCP non-fragment, so the `fwd_nodes > total` check (`telemetry_schema.py:221`) is only a one-sided sanity check and the doc line "definisi = FlowMonitor timesForwarded" is inexact for the per-node column.

### Energy comparison precision

`telem::Finalize` and `Write` print `self_energy_j` at 10 significant digits, but the reference value `sensor_energy_consumed_J` goes into `metrics_*.csv` through a stream with no `setprecision`, so it has 6 significant digits. For a value such as 85.1234 J the rounding error is up to 5e-5 J while `validate` accepts `max(1e-6, 1e-7*|ref|)` = about 8.5e-6. Any scenario with consumption above roughly 10 J will fail the "energy per window = source energy" check, and `telemetry_eval.py` exits non-zero through `all_valid`. The unit test uses exact synthetic numbers, so it cannot see this. Integer counters in the same file are unaffected by stream precision.


### Strict FlowMonitor equality

The definitions match `Ipv4FlowProbe` for UDP, but `FlowMonitor::ReportForwarding` silently ignores packets not in `m_trackedPackets`, and entries are erased on `ReportLastRx`, on `ReportDrop`, and by the lost-packet sweep (default 10 s). The simulation contains TCP `OnOff` flows (`:986-994`). A retransmitted TCP segment keeps the first transmission's `Ipv4FlowProbeTag`, so `SendOutgoingLogger` does not re-register it, and a forward after the original was delivered or dropped is counted by telemetry but not by FlowMonitor. Whether this happens depends on loss on the user-to-cloud path, which I could not check. 

### Rxfail bucket and trust bias

The classifier reads `g_failT[i]` for any RX failure of any frame at the observer in `[t_ack, t_ack+wdLate]`. For a forwarded packet this is irrelevant (it is heard). For a dropped packet, a nearby failure moves it from `clean` (negative evidence) to `rxfail` (discarded). In a dense or busy cell most 1 s windows contain a failure, so the discard probability tracks channel load rather than anything about j. The estimator `F/(F+U)` therefore rises for malicious relays as load rises; it also explains why the 0.30 grayhole target will read high in `est` and why `lo/hi` bounds exist. The docs say rxfail "can absorb many watches" but present it as neutral; it is asymmetric. The audit categories `j_tx_rxfail_at_observer` versus `j_ip_drop_route_error` inside `unobserved_rxfail` will quantify this on the pilot.

### Silent misses in unobserved_clean

Frames that never reach `PhyRxDrop` or `RxOutcome` (observer transmitting without a drop trace, signal below detection) leave no failure record, so they land in `clean` and count against j. The audit's `j_tx_no_rx_event_at_observer` row measures this. The trust step currently has no gate on that rate.

### Residual leak surface in the node CSV

The static label test only greps `telem` text. The node CSV itself carries `self_ip_drop_route_error`, which in this simulation equals grayhole drops, so the label is recoverable from telemetry by any consumer that reads `self_*`. Trust ignores those columns; the guard is convention plus a unit test, not structure.

### Test coverage

Python is covered with synthetic data only. Not tested: any C++ behaviour, the energy precision interaction with real metrics, TCP-heavy FlowMonitor equality, and the audit-versus-category cross check on non-synthetic data.
